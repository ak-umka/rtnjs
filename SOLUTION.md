# Решение

## Что сделано

**Скидки в `daily-totals`.** Миграция `002_discounts.sql` добавляет в `orders` поля `discount_percent` и `amount_paid_kop`. При нормализации заказа `discountPercent` и `amountPaid` принимаются числом или строкой (API отдаёт и так, и так). Ответ: `{ date, total, gross, discount, net }`, где `total = gross`. Всё считается в копейках, в рубли переводится только на выходе.

- `net` — сумма `amountPaid`: в задании это «сколько фактически заплатили», поэтому значение берётся из API как есть, а не пересчитывается из процента.
- Если `amountPaid` нет (заказы старого формата: таких 1177 из 5030), `net` считается из `discountPercent`, а без него скидка считается нулевой.
- Отклоняются с 400: процент вне 0..100, `amountPaid > amount`, мусор в полях.

**Расхождение по c_7.** Исправлено, подробности ниже.

**Попутные исправления:**
- `toKop` терял копейку из‑за ошибки double: `1217.61 * 100 = 121760.99999999999`, `Math.floor` давал `121760`. На `amount` это не проявлялось, потому что в данных там целые рубли. А на `amountPaid` таких значений 96, и `net` был бы занижен. Теперь перед отбрасыванием долей результат округляется через `toFixed(4)`. Поведение «доли копейки отбрасываем» (`10.999 → 1099`) осталось прежним.
- Гонка в вебхуках. `apply` делал «прочитать → сравнить → записать» в два запроса, а внешняя система шлёт дубли одного заказа одновременно (в логе видно 6 доставок за 1–2 мс). Старая версия могла перезаписать новую. Теперь это один `INSERT … ON CONFLICT DO UPDATE … WHERE orders.updated_at < excluded.updated_at`, а `created/updated/stale` определяется через `RETURNING (xmax = 0)`.

## Причина расхождения из жалобы

`TotalsService.daily` вычислял смещение таймзоны **один раз, на текущий момент** (`tzOffsetMinutes(timezone, new Date())`), и применял его ко всем заказам периода. Таймзона c_7 — `Europe/Berlin`. 29.03.2026 Берлин переходит с CET (+1) на CEST (+2). Сейчас ноябрь, смещение +1, поэтому заказы 29–31.03, сделанные с 22:00 до 23:00 UTC (это уже следующие сутки по Берлину), попадали в предыдущий день. 27–28.03 совпадали. Летом картина была бы зеркальной: ломались бы 27–28.03. То есть отчёт ещё и зависел от даты запуска.

| дата | было (total) | стало |
|---|---|---|
| 27.03 | 24736 | 24736 |
| 28.03 | 58233 | 58233 |
| 29.03 | 43964 | 34658 |
| 30.03 | 52201 | 59684 |
| 31.03 | 44064 | 35401 |

Исправление: смещение берётся на момент каждого заказа (`dateInTimeZone(createdAt, tz)`). Форматтеры `Intl` кэшируются по таймзоне.

Как нашёл. Выгрузил все заказы из внешнего API и посмотрел заказы c_7 за 26.03–01.04. Они кучно стоят у полуночи по Берлину (22:15, 22:40, 23:20, 23:50 UTC). Затем увидел, что в коде смещение берётся на `new Date()`, и вспомнил, что последнее воскресенье марта — день перехода на летнее время. Подтвердил независимым расчётом (см. ниже).

   - `test/discounts.test.ts`: gross/discount/net, пример из задания, старый формат, строковые поля, копеечная точность, обновление скидки вебхуком, валидация, сохранение скидок при синке.
   - `test/webhooks.test.ts`: конкурентные дубли и версии не по порядку, одновременное создание (ровно один `created`).
   - `money` и `time`: юнит-тесты на новые функции.
2. Посмотрел на поведение внешнего API без нашего сервиса:
   - выгрузил `/orders` целиком (5030 заказов, 52 страницы);
   - поймал все 92 вебхука своим сервером-заглушкой и сравнил их с данными синка.
3. `result.json` получил строго по регламенту: `docker compose down -v && up -d`, `migrate`, `npm start`, `POST /sync` (`applied: 5030, invalid: 0`), вебхуки (92 × 200), запрос `daily-totals`.
4. Сверил `result.json` с независимым скриптом. Он берёт сырые данные API и вебхуков, оставляет последнюю версию заказа по `updatedAt`, определяет дату через `Intl` в Europe/Berlin и суммирует в копейках. Совпало до копейки по всем пяти дням.

## Что ещё заметил

- **API**: `amount` и `discountPercent` иногда приходят строкой, `createdAt` иногда без `Z`. Иногда вместо 429 приходит 200 с `{"error":"rate_limited"}` (у меня это случилось 3 раза на 55 запросов). В конце выдачи приходит пустая страница с тем же курсором. Курсор — это base64 от `o:<offset>`, то есть пагинация по смещению: если заказы добавятся во время синка, возможны пропуски или дубли (дубли не страшны, их отсекает `updatedAt`).
- **Вебхуки**: каждый приходит 2–3 раза, почти одновременно и не по порядку. Тело — полный снимок заказа, так что правило «побеждает больший `updatedAt`» корректно.
- **Синк** заканчивается на любой пустой странице (`items.length === 0`). Если API когда-нибудь отдаст пустую страницу посреди выдачи, мы молча остановимся раньше времени. Сейчас такого нет, поэтому не трогал.
- **Возвраты**: `refunded` убирает заказ из суммы задним числом, и цифра за прошлый день меняется. Скорее всего, так и задумано, но с отчётом платёжной системы (если там возврат — отдельная операция) это тоже может расходиться.
- **Таймзона** клиента кэшируется навсегда, сменить её можно только руками в БД.
- В `README` указана Node 20+, но `engines` никак это не проверяет.

## Допущения

- `net` берётся из `amountPaid`, а не пересчитывается из `discountPercent`. В данных они везде согласованы.
- Нет полей скидки — значит, скидки нет.
- Деньги округляются вниз до копейки, по уже принятому в коде правилу.
- Изменил три существующих assert'а в `test/totals.test.ts`. Они сравнивали ответ через `toEqual` со старой формой `{date,total}`, а новая форма задана самим заданием. Ожидания для `total` не менялись, к ним добавились `gross/discount/net`.
- После миграции у уже сохранённых заказов `net = gross` до ближайшего синка. На проде миграцию надо сопровождать `POST /sync`.

## Что бы доделал

- Флаг `refetch` или фоновый пересинк после миграции, чтобы заполнить скидки у старых данных.
- Сделать `/sync` асинхронным со статусом в `sync_runs`. Сейчас HTTP-запрос висит около 16 секунд.
- Хранить историю статусов (время оплаты и возврата), чтобы при необходимости строить отчёт по дате платежа, а не по дате создания заказа.
- Добавить метрики и алерты на `invalid` в синке.
